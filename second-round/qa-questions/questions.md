## 二面（1–2 小时）

**目标**：看深度、动手能力和 AI 协作方式。多聊技术，少问答：项目深挖用聊的方式，算法和组件题是动手环节。

**顺序建议**：先聊项目热身，再做算法，然后做组件题，最后聊 AI 协作。算法放在组件题之前，是因为组件题耗时长，中途不要被打断。

## 二面·A 项目深挖题库

**二面用法**：不逐块问。根据简历挑 3–4 块深聊（建议 30–40 分钟），把“追问阶梯”当作聊天的线索，而不是问卷；候选人基础没问题的块直接跳过。

**通用打法**：先开放提问，再三层追问：做了什么 → 为什么这么做（有没有对比过别的方案）→ 出了什么问题、结果数据是多少。真做过的人越问越细，没做过的人到第二层就开始含糊。

**每块的读法**：“正确方向”是一个好回答应该走的步骤；“错误方向”是常见的错误做法，括号里是它错在哪。候选人不需要逐字对上，方向对、能讲出原因即可。

**页面白屏与首屏慢、加载优化的边界**（容易混，开场就要分清）

| 题目 | 症状 | 题型 | 考察什么 | 不该变成什么 |
| --- | --- | --- | --- | --- |
| 页面白屏 | 页面“出不来”，是故障 | 排障题：给症状，讲完整路径 | 系统性排障、先止血、对监控和上报的认知 | 不该聊性能优化手段 |
| 首屏慢与加载优化 | 页面“出得慢”，是性能问题 | 同一主题的两种问法：假设型（给症状，讲怎么定位优化）和经历型（问做过什么） | 指标体系、分层定位、优先级、真实数据 | 不该答成故障排查 |

**判断方法**：白屏看有没有“先缩小范围、先止血”的结构；首屏慢和加载优化看有没有指标和分层，经历型再看有没有真实细节和数字。候选人把白屏答成性能优化，或把性能问题答成故障排查，说明没分清边界；把加载优化答成一串手段清单，往往说明没真正做过。

### A.1 页面白屏排查

**考察目标**：系统性排障思维；对监控与排查工具的认知。

**开场**：“线上用户反馈页面打开白屏，只出现在一部分用户身上。从你看到这条消息开始，完整讲一遍你的排查路径。”

**追问阶梯**

1. 你怎么缩小范围？
2. 怎么区分是资源加载失败、JS 报错、接口异常还是渲染错误？
3. 本地复现不了怎么办？
4. 怎么先止血？
5. 怎么防止再发生？

**正确方向（怎么做）**

1. 先缩小范围：浏览器、系统、地区、版本、是否在灰度、是否集中在某个网络环境。
2. 看监控和报错平台（Sentry 类），用 sourcemap 还原堆栈；没有监控就让用户提供控制台和网络面板信息。
3. 分类定位：资源加载失败（CDN 缓存了旧文件、文件被删、跨域）、JS 报错（兼容性、语法过新）、接口异常（返回意外数据）、渲染错误（服务端渲染水合失败、未捕获的异常导致整棵树卸载），也要想到内容安全策略（CSP）拦截了脚本。
4. 先止血再找根因：回滚版本、关闭灰度、必要时清 CDN。
5. 防止再发生：错误边界、降级页面、错误上报带版本号、发布后错误率告警。

**错误方向**

- 一上来就猜原因（没有“先定位再修复”的结构）
- 说“本地复现不了就没办法”（线上问题要靠监控数据，而不是靠复现）
- 先查根因再决定是否回滚（用户一直在受影响）
- 没有监控也没有上报（下次依然靠用户反馈发现）
- 修完就结束（没有防止再发生的机制）

### A.2 首屏慢与加载优化

**考察目标**：有没有先测量再优化的习惯；能否分层定位瓶颈；有没有优先级判断；结果能否量化。同一个主题有两种问法：假设型（给症状，看方法）和经历型（问做过什么，看真实细节和数字），两种都要能答。

**开场（二选一，或先后都问）**

- 假设型：“用户反馈页面首屏加载慢，你会怎么定位和优化？”
- 经历型：“你们项目的加载性能怎么样？你做过哪些优化？”

**追问阶梯**

1. “慢”具体指哪个指标？实验室数据和真实用户数据有什么区别？
2. 瓶颈在网络层、资源层还是渲染层，你怎么判断？
3. 为什么先动这一项？还有哪些没动？
4. 优化后数据变化多少？上线后怎么确认？
5. 怎么防止以后又变慢？

**正确方向（怎么做）**

1. 先定义“慢”并测量：LCP、FCP、TTFB、INP、CLS。实验室数据（Lighthouse）用来找问题类型，真实用户数据（RUM、Performance API 上报）看 p75，不看平均值。
2. 分层定位：网络层（DNS、TCP、TTFB、CDN 命中）→ 资源层（JS 和 CSS 体积、图片、字体）→ 渲染层（长任务、阻塞渲染、请求瀑布）。
3. 对症处理，先抓大头：TTFB 慢就静态化、加缓存、优化查询；体积大就用 bundle analyzer 找大头、做懒加载和 Tree Shaking，检查服务端依赖有没有被打进客户端；有瀑布就并行请求、在服务端提前取数据、用 `preload` 与 `preconnect`；图片用 AVIF 或 WebP、配 `srcset`，首屏大图设 `priority`。
4. 一次只改一类，改完用同一个指标对比，给出“LCP 从 X 到 Y”这样的数字。
5. 结合业务讲取舍：骨架屏改善体感，但不改变真实指标；说得出哪些没做以及为什么。
6. 防止退化：设性能预算，在 CI 里检查。

**错误方向**

- 只背“压缩图片、用 CDN、懒加载”这类零散手段（没有指标，说不清瓶颈在哪一层）
- 只看 Lighthouse 跑分，分不清实验室数据和真实用户数据（本地好看不代表用户快）
- 看平均值（掩盖了最慢的那批用户）
- 首屏大图也懒加载（会拖慢 LCP）
- 同时改很多项（无法判断哪一项起了作用）
- 说不出优化前后的数字（经历型问题下，很可能没真正做过）
- 把骨架屏当成解决了“慢”（只是体感，指标没变）
- 答成故障排查的思路（把“慢”和“白屏”混为一谈）

### A.3 和后端对接数据

**考察目标**：分层与解耦意识；对“后端变化扩散到前端”的防范；有没有考虑提交（写回）方向。

**开场**：“30 个接口，后端字段命名不统一、偶尔会改，前端怎么组织请求、类型和转换？”

**追问阶梯**

1. 组件里用的是后端原始字段，还是你们自己定义的结构？
2. 后端把某个字段改名，你要改几处？
3. 表单提交回去怎么转换？金额单位、日期、枚举有没有处理？
4. 你怎么知道后端实际返回的数据符合类型？
5. 什么情况下你会省掉这一层？

**正确方向（怎么做）**

1. 分三层：请求层只管取数，校验层确认数据形状，适配层把后端结构（DTO）转成前端用的结构（ViewModel）。
2. 组件只依赖 ViewModel，不碰后端字段。后端改名时，只改适配函数一处。
3. 适配层统一命名风格、空值（null 与 undefined）、枚举、日期和金额单位。
4. 提交时做反向转换；需要乐观锁就保留版本号或更新时间，不要靠“覆盖后再猜回去”。
5. 类型尽量自动生成（OpenAPI 或 CMS 自带的类型），运行时用 Zod 之类校验外部数据。
6. 后端字段本来就规范、前端原样展示时可以省掉这一层，说明会按场景取舍。

**错误方向**

- 直接覆盖原字段（丢掉原始值，提交时无法还原）
- raw 和 formatted 两套数据一起往下传（组件要自己判断用哪个，容易用错、容易不同步）
- 在每个组件里就地处理后端字段（后端改名要改所有组件，格式化逻辑散落）
- 靠“多沟通、让后端别改”（没有机制保障，下次还会出问题）
- 认为 TypeScript 类型就能保证运行时数据正确（类型只在编译期有效）

### A.4 环境变量泄漏到客户端

**考察目标**：对 Next.js 服务端与客户端边界的理解；安全意识；应急处理。

**开场**：“`NEXT_PUBLIC_` 是什么意思？你怎么保证密钥不会泄漏到前端？”

**追问阶梯**

1. 除了误加前缀，还有哪些路径会把密钥带到前端？
2. 你用什么机制在构建期拦住它？
3. 同一个镜像要部署到多个环境，客户端配置怎么处理？
4. 发现已经泄漏，你第一步做什么？

**正确方向（怎么做）**

1. 理解机制：`NEXT_PUBLIC_` 变量在构建时被内联进客户端 JS，任何人都能看到，只放公开信息。
2. 知道真正的泄漏路径：含敏感字段的对象作为 props 传给客户端组件（会序列化进 HTML 和 RSC payload）、客户端间接引入了服务端模块、错误信息和日志带出密钥、`.env` 进了 Git 或镜像层、sourcemap 公开。
3. 数据访问层只返回页面需要的字段，不把完整的用户或配置对象传给客户端组件。
4. 服务端模块顶部加 `import 'server-only'`，被客户端引入时构建报错；用 Zod 之类校验环境变量，服务端与客户端变量分开声明。
5. CI 里加密钥扫描，密钥按环境隔离、最小权限。
6. 应急顺序：先立刻轮换密钥，再清理代码，最后排查日志看有没有被滥用。

**错误方向**

- 为了让客户端能读，给密钥加 `NEXT_PUBLIC_`（等于公开）
- 只知道前缀规则，不知道 props 序列化这条路径（最常见的真实泄漏却防不住）
- 把整个用户对象或配置对象传给客户端组件（敏感字段会跟着发出去）
- 同一个镜像改环境变量，期待客户端值跟着变（构建时已经内联，不会变）
- 泄漏后只删代码或清 Git 历史（密钥一旦暴露就应视为已泄漏，必须轮换）
- 日志里直接打印完整配置或请求头（密钥进了日志系统）

### A.5 SEO 与渲染方案选型

**考察目标**：对搜索引擎工作原理的理解；渲染方案的选型能力；SEO 与业务目标是否匹配。

**开场**：“如果站点需要做 SEO，从前端角度你会做哪些事？SPA 项目的 SEO 怎么处理？”

**追问阶梯**

1. 要不要做 SEO？哪些页面不需要？
2. SPA 的 SEO 问题根源是什么？
3. SSR、SSG、ISR、动态渲染怎么选？
4. 怎么验证优化有没有生效？

**正确方向（怎么做）**

1. 先问要不要做：内容型站点（官网、文档、电商详情页）要做；后台系统、登录后的页面不需要。
2. 渲染方案是核心决策：纯 CSR 对爬虫不友好（执行 JS 能力有限、抓取延迟、社交分享卡片抓不到内容）；SSR 实时但服务器成本高，SSG 适合低频更新，ISR 是两者折中，动态渲染（对爬虫返回预渲染版本）作为补救。
3. 技术清单：语义化 HTML，每页唯一 `h1`；`title`、`description`、Open Graph、JSON-LD；真正的 `<a href>` 链接；canonical、`sitemap.xml`、`robots.txt`；URL 可读、避免 hash 路由；多语言用 `hreflang`；Core Web Vitals 达标；图片 `alt`。
4. 验证闭环：在 Search Console 或百度站长平台提交收录，用 `curl` 或网址检查工具看爬虫实际拿到的 HTML，持续监控收录量和关键词排名。

**错误方向**

- 只会说“加 meta 关键词”（现代搜索引擎基本不看）
- 不知道 SPA 的 SEO 问题根源
- 推荐 SSR，却说不清成本（服务器、缓存、水合复杂度）
- 把 SEO 当成纯前端的事（内容质量和外链才是权重主体）
- 给后台系统做 SEO（没有想过业务目标）

### A.6 AI 工具链：Skill、MCP 与团队分享

**考察目标**：对 AI 开发工具链的真实了解程度；是不是只会用，还是会配置、会沉淀、会分享给团队；对安全和上下文成本有没有意识。

**开场**：“你们日常用哪些 AI 开发工具？你怎么让它在项目里按规范干活，又怎么把自己做好的东西分享给团队？”

**追问阶梯**

1. 项目规则文件（如 `CLAUDE.md`、`AGENTS.md`）里你写什么、不写什么？
2. Skill 和 MCP 有什么区别？各自什么时候用？
3. 你做过 Skill 吗？怎么设计的？怎么分享给同事？
4. 接过哪些 MCP？自己写过吗？密钥和权限怎么管？
5. hooks、subagent 用过吗？分别解决什么问题？
6. 你怎么判断一个 Skill 或 MCP 真的有用？

**正确方向（怎么做）**

**① 先分清各自的职责**

| 机制 | 它是什么 | 适合什么 |
| --- | --- | --- |
| 规则文件 | 常驻上下文的项目约定 | 技术栈、目录结构、命令、禁区，保持精简 |
| Skill | 一个带说明的文件夹，按需加载 | 可复用的工作流和领域知识，如发布流程、代码评审清单 |
| MCP | 连接外部系统的标准协议，提供工具和数据 | 访问 Issue、数据库、设计稿、内部系统 |
| Hooks | 在特定事件自动执行的脚本 | 必须每次都做的确定性动作，如提交前格式化 |
| Subagent | 独立上下文的子任务执行者 | 大范围搜索、并行调研，避免污染主上下文 |

**② 做一个好 Skill**

1. 一个文件夹，核心是 `SKILL.md`：开头写 `name` 和 `description`，后面是步骤；需要时附脚本和参考资料。
2. `description` 要写清楚“什么场景下该用”，因为触发主要靠它；正文保持精炼，大块资料拆成单独文件按需读取。
3. 能用脚本确定完成的部分交给脚本，不要全靠模型临场发挥。

**③ 怎么分享**

1. 团队内部：放进项目仓库（如 `.claude/skills/` 这类目录），随代码走，改动走 PR review。
2. 跨项目：打包成插件或包，通过团队的内部市场或 registry 分发；写 README、版本号和变更记录。
3. 不在里面放密钥和个人路径；写清楚依赖和使用前提。

**④ 接入和编写 MCP**

1. 优先用成熟的现成 server；自己写就用官方 SDK，先只做只读工具，工具名、描述和参数 schema 写清楚。
2. 本地用 stdio，团队共享用远程 HTTP 加授权。
3. 项目级配置文件（如 `.mcp.json`）可以提交仓库，密钥走环境变量，不入库。

**⑤ 上下文成本与安全**

1. 装得越多，工具描述占用的上下文越多，也越容易选错工具；只启用当前任务需要的。
2. 网页、Issue、文档里的内容可能带有提示注入；有写权限的工具要人工确认，凭据遵循最小权限，优先用测试环境。

**⑥ 验证效果**：选几个固定的真实任务，对比有无该 Skill 或 MCP 时的结果和耗时，并观察它是否在该触发时触发。

**错误方向**

- 把所有规范塞进一个超长的规则文件（占上下文，重点被稀释）
- 把固定流程做成 MCP，或把需要连接外部系统的事塞进 Skill（选错了机制）
- Skill 的 description 写得很笼统，如“帮助写代码”（不会被触发，或乱触发）
- 分享靠发文件、群里贴（没有版本、没有 review、难以更新）
- 把 token 或密钥写进 `.mcp.json` 或 Skill 后提交（密钥进了仓库）
- 一次装十几个 MCP（上下文膨胀，工具选择变差）
- 给 MCP 开生产库的写权限，对外部内容不设防（提示注入可能被利用）
- 只会列工具名字，说不出自己配置或做过什么（可能只是用过，没有自己配置或沉淀过）
- “感觉有用”，没有对比和验证（无法判断是不是真的提效）

## 二面·B 手写算法

**题池**

| 题目 | 考点 | 参考思路 | 追问 |
| --- | --- | --- | --- |
| 数组扁平化 | 递归、迭代 | 递归，或用栈迭代，支持指定深度 | 不用递归怎么写？深度很大会怎样？ |

**推荐组合**：两数之和或有效括号（任选一）加扁平数组转树；候选人偏弱就用两数之和加防抖；候选人很强，再用并发请求池替换其中一道。

**评分要点**

- 先说思路再写，能说出时间复杂度
- 处理边界：空输入、重复、不合法数据
- 命名清楚，代码可读，不过度炫技
- 写完能自己构造几个测试用例验证
- 卡住时的表现：给一个提示后能不能继续推进

**错误方向**

- 上来就写，没有思路表达
- 只能写出暴力解，被提示后也无法优化
- 完全不考虑边界，写完不验证
- 背过的题能写，换一个条件就写不出（说明是背的）

### B 参考解法（面试官对照）

只看思路和边界，不要求和下面一模一样。

**数组扁平化（可指定深度）**：递归时每进一层深度减一。追问“不用递归”：用栈迭代；深度极大时递归会栈溢出。

```js
function flatten(arr, depth = Infinity) {
  const result = [];
  for (const item of arr) {
    if (Array.isArray(item) && depth > 0) result.push(...flatten(item, depth - 1));
    else result.push(item);
  }
  return result;
}
```

**追问 1**
 问：「你把这段代码讲一遍，递归那一行为什么这么写？」
 期望回答：遇到数组时，它里面可能还有嵌套，处理方式和外层完全一样，所以调用自己把它拍平，再把拍平后的元素放进结果。不是数组就是最终的元素，直接放进去。遇到空数组，循环一次都不进，自然结束。
 弱回答信号：只会复述“这里调用了 flatten”，说不出为什么要调用自己；说不清什么时候停止。

**追问 2**
 问：「如果只想拍平一层，要怎么改？」
 期望回答：加一个深度参数 `depth`。递归时把 `depth` 减一，`depth` 为 0 时不再展开，直接把这个元素放进结果。或者不用递归，直接 `[].concat(...arr)`，它只拍平一层。
 怎么评价：当场改出来是好；给一句提示（“能不能让函数知道自己还要展开几层”）后改出来也合格；改不出来说明对递归的理解还停留在背代码。

**追问 3**
 问：「如果嵌套特别深，比如十万层，会怎样？」
 期望回答：递归每深入一层，就在调用栈上多占一层，层数太多会报栈溢出（`RangeError: Maximum call stack size exceeded`）。解决办法是不用递归，改成循环加一个自己维护的“待处理清单”（栈）。
 弱回答信号：只说“会很慢”或“内存不够”，没有说到调用栈。答出栈溢出是加分，答不出不扣分。

**追问 4**
 问：「不用递归，怎么写？」
 期望回答：准备一个数组当栈，放进所有待处理的元素；循环取出一个，是数组就把它的内容放回栈里，不是就放进结果；栈空了结束。注意从末尾取，所以放回时要倒着放，否则顺序会反。另一种写法是 `while (arr.some(Array.isArray)) arr = [].concat(...arr)`，每轮拍平一层，直到没有数组。
 怎么评价：能说出“用循环加栈”的思路就算过关，不要求当场写对。如果写了，检查顺序有没有反：用 `[1, [2, [3]]]` 跑一遍，应该是 `[1, 2, 3]`。顺序反了，提示“取的时候是从前面还是后面”，看他能不能自己想到要倒着放。

## 二面·E AI 协作与认知

这一组放在最后。前面考的是具体技术，这里看的是候选人在 AI 时代的工程判断：AI 提升了代码产出速度，但验证、设计判断和质量责任的价值反而上升了。顺序是：团队流程 → 个人实践 → 评审标准 → 自我定位。

### D.1 AI 生成代码的治理

**考察目标**：工程管理者视角、质量与风险意识、流程设计能力。

**开场**：“团队里 AI 生成的代码越来越多，你觉得需要在流程和规范上做哪些治理？”

**追问阶梯**

1. 哪些模块不允许直接合入 AI 生成的代码？
2. 怎么标注，出了问题谁负责？
3. 怎么让 AI 的产出更贴合团队规范？
4. 敏感代码和许可证怎么管？

**正确方向（怎么做）**

1. 承认价值，管理风险：不一刀切禁止，把 AI 产出视同初级工程师的产出，用同样的审查标准。
2. 流程层面：commit 或 PR 里标注；鉴权、支付、数据删除等关键模块不直接合入；Review 的责任在人，不在工具。
3. 质量兜底：静态检查、覆盖率门禁、严格的类型检查；用测试描述意图，让 AI 代码必须通过测试。
4. 知识沉淀：把团队规范、目录约定、常用模式写成 AI 可读的上下文（规则文件），让生成质量前置提升，而不是事后返工。
5. 安全合规：敏感代码不脱敏不上传第三方模型；关注许可证污染风险。

**错误方向**

- 一刀切全禁（团队效率损失，而且禁不住，会变成私下使用）
- 随便用，出了事再说（没有任何兜底）
- 只谈个人使用技巧，没有团队流程视角
- 只要求标注，却不调整审查标准（标注没有意义）
- 认为责任在工具（出了问题没人负责）

### D.2 AI 协作的边界

**考察目标**：是否真用过 AI 工具；有没有验证产出的习惯；对 AI 能力边界的真实认知，尤其是前端领域的具体鉴别力。

**开场**：“聊聊你最近一次用 AI 辅助开发的经历：它帮上忙的是什么地方，它翻车的是什么地方，你当时怎么发现的？”

**追问阶梯**

1. AI 写的前端代码有哪些特有的坑？
2. 样式类的问题你怎么发现？（这类最难）
3. 拿到 AI 生成的一个组件，合入前你验证什么？
4. 哪些事你明确不交给 AI？

**正确方向（怎么做）**

1. 能讲出具体的翻车案例（编造的 API、过时的语法、隐蔽的边界 bug、看似合理实则错误的状态管理），并说清当时怎么发现的。
2. 能列出前端特有的翻车点：
   - 过时或编造的 API：React 旧生命周期、Vue 2 与 3 语法混搭、不存在的 CSS 属性；
   - 样式：响应式断点错乱、暗色模式漏配、z-index 冲突、固定像素在移动端出问题；
   - 状态：闭包旧值、effect 依赖漏写、受控与非受控混用；
   - 无障碍：`div` 当按钮、缺键盘操作和焦点管理；
   - 性能：多余重渲染、大列表不虚拟化、监听不清理。
3. 验证流程：类型检查 → 单元或交互测试 → 亲自在浏览器里点一遍关键路径 → 视觉回归或截图对比兜底。
4. 知道分工：样板代码、测试、范围明确的重构适合交给 AI；架构决策、安全相关逻辑、自己没法验证的东西必须自己把关。

**错误方向**

- “AI 写的我都直接用”（没有验证习惯）
- “我完全不用 AI”（在如今可能意味着学习意愿低）
- “AI 写的前端代码我 review 一遍就合”（样式和交互问题，光读代码发现不了）
- 举不出任何前端翻车的案例（说明要么没用过，要么用得很浅）

### D.3 代码评审标准的变化

**考察目标**：工程品味、质量把控意识。

**开场**：“如果团队里初级工程师大量用 AI 生成代码，Code Review 的重点应该发生什么变化？你会重点看什么？”

**追问阶梯**

1. AI 生成的代码有哪些典型问题？
2. 你怎么判断一段代码是“看起来对”还是“真的对”？
3. 你会要求作者做什么，才能放心合入？
4. 哪些问题交给工具，哪些必须人来看？

**正确方向（怎么做）**

1. 重点从“语法对不对”转向“设计合不合理”：状态模型、副作用边界、错误处理、可测试性。
2. 留意 AI 常见的问题：过度抽象、重复模式堆砌、注释与实现不符、顺手改了无关代码。
3. 要求作者能讲清每一段代码在做什么；讲不清的不合入。
4. 把能自动化的交给工具（格式、lint、类型、测试），人专注于风险和设计。

**错误方向**

- 只看命名和格式（没有抓到设计层面的问题）
- 对 AI 代码一律放行，或一律怀疑（没有判断依据）
- 不要求作者解释，合入自己讲不清的代码
- 把 Review 变成逐行挑风格（这些该交给工具）

### D.4 前端不会被 AI 取代的部分

**考察目标**：自我认知、成长性。

**开场**：“你觉得未来三年，前端工程师身上最难被 AI 替代的能力是什么？你自己在刻意练哪一项？”

**追问阶梯**

1. 在你的工作里，这种能力具体体现在哪件事上？
2. 你是怎么练的？
3. 你觉得哪部分工作会最先被替代？

**正确方向（怎么做）**

1. 谈到需求理解、体验取舍、性能与兼容性这类需要上下文的决策、跨团队沟通。
2. 能结合自己的实践举出具体例子，而不是只讲概念。
3. 对自身价值有清晰的思考，也敢承认哪些工作会被替代，并说出自己的应对。

**错误方向**

- 泛泛而谈“创造力、沟通”，举不出自己的例子
- 认为“没有什么是 AI 替代不了的”（缺乏对自身价值的思考）
- 认为“AI 会替代一切”（消极，没有应对）
- 只讲技术名词，回避“自己在练什么”
